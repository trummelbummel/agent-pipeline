<objective>
SR-013 is the last open item in the senior review backlog and the only one that changes no behaviour. `claim_pipeline.py` is 1414 lines and holds five different jobs at once: the LangGraph topology, the coverage router (SR-004), the per-coverage medical rule matrix (SR-010), the checker runner and its legacy-boolean mapping (SR-008), the document-acceptability policy, the ordered decision fold, the analysis-payload builder, and the claim-artifact reads. Nine of the thirteen backlog tasks landed in this one file, which is exactly the "branch accretion" pattern the review named. The cost is visible in the tests: `tests/test_workflows/test_claim_pipeline.py` is 2934 lines, and almost every policy assertion is made by seeding a claim folder on disk, compiling a `StateGraph`, and feeding a `MagicMock(side_effect=[...])` whose element order must match the classifier/checker call order — so asserting one precedence rule costs a graph run, and reordering a checker call breaks unrelated tests.

This plan moves the policy out and leaves the orchestration behind. A new `compliance/policy/` package (D-01) holds the rules as plain functions over plain data: `route_coverage`, `rule_set_for_claim`, `run_checks`, `is_missing_documentation`, `decision_from_state`, `analysis_result_payload`. Nothing under `compliance/policy/` touches the filesystem — the claim-artifact reads move to a separate `ClaimArtifactReader` in `compliance/workflows/`, and the pipeline passes what it read into policy as arguments. That single constraint is what buys the testability the backlog asks for: the decision fold becomes a function of a state dict and two values, so its whole precedence order can be proved without a graph, a chat mock or a `tmp_path`.

Nothing about the policy itself changes (D-02). This is a move, not a rewrite: the SR-004 highest-probability routing with config-order tie-break, the SR-010 medical gating and `checker_skipped` trace, the SR-008 outcome precedence and the exact `decision_explanation` strings, the fixed checker mode order that existing `side_effect` sequences depend on, and the presence-versus-absence of every boolean key in `analysis_result.json` all survive byte-identical. The one restructure that is not a pure move is the decision fold, which is rewritten from a chain of eight `if` blocks into a table of ordered gates — because that is what clears C901 by structure rather than by suppression, which the backlog names as the acceptance bar.

Locked decisions (from CONTEXT.md and `.gsd/steering-decisions-2026-09-29.md` SR-013):
- D-01: New package `compliance/policy/`.
- D-02: Behaviour-preserving extract now (SR-008 / SR-010 / SR-011 already landed); do not combine with new policy changes.
- D-03: Public surface is `ClaimPipeline` plus thin helpers; policy internals stay private.

Planner discretion (flagged; report in SUMMARY):
- P-01: Eight modules, split by the seam that already exists in the code, not by size: `coverage.py` (SR-004 router), `state.py` (the shared `ClaimAnalysisState` contract), `rules.py` (SR-010 matrix), `checks.py` (checker runner + legacy booleans), `documents.py` (acceptability), `decision.py` (the fold + HITL resolution), `payload.py` (artifact body), and `__init__.py` (the thin surface). Each corresponds to one backlog task that already shipped, so a future policy change touches one file.
- P-02: `ClaimAnalysisState` moves into `compliance/policy/state.py` rather than staying in the pipeline. It is the data contract *between* the graph and the policy, and leaving it in `claim_pipeline.py` would make every policy module import from the orchestrator — the wrong direction, and a cycle the moment the pipeline imports policy. Nothing outside `claim_pipeline.py` imports the name today, so the move costs no caller churn.
- P-03: Policy is filesystem-free, enforced by moving the artifact reads into `ClaimArtifactReader` and passing the results in. `decision_from_state` takes `ocr_failure_reason: str | None`; `analysis_result_payload` takes that plus `metadata_run_id`. This is the change that makes the fold unit-testable at all, and it also removes the repeated `document_metadata.json` reads the current code performs (the fold is evaluated four times per persist, each time re-reading the file).
- P-04: The reader preserves today's two different roots exactly. `_document_ocr_failure` is called with no `input_root`, so it reads `preprocessed_dir/{claim_id}`, while `_document_metadata_run_id` is called with the claim input root — on the `process_then_analyze` path with a raw claim folder these are different directories. That asymmetry looks unintended, but changing it would change decisions, so the pipeline constructs two readers and the discrepancy is recorded as a follow-up rather than silently fixed (D-02).
- P-05: Graph topology stays in the pipeline: the branch-to-next-node map, `CoverageNextNode`, the node functions, `BatchAnalysisResult` and the soft-fail batch loop are orchestration, not policy. `route_coverage` returns a branch; only the pipeline knows which node name serves that branch.
- P-06: Functions exported from a policy module carry no leading underscore; helpers inside a module do. This deliberately differs from the neighbouring `claim_dates.py`, whose cross-module functions are underscore-prefixed — that convention makes a module's real surface unreadable, and D-03 asks for an explicit thin surface. `claim_dates.py` is left untouched.
- P-07: Two levels of surface. `compliance/policy/__init__.py` exports only what `ClaimPipeline` calls (D-03); each module additionally declares its own `__all__` for the helpers that unit tests and sibling policy modules use (for example `legacy_booleans_from_outcomes`). Tests import from the module, not the package.
- P-08: `decision_from_state` is restructured into an ordered table of `(predicate, explanation)` gates evaluated in sequence. Precedence and explanation strings are unchanged; this is the structural fix that takes the fold from complexity 8 to inside a stricter-than-configured gate, which is the difference between the backlog's "cleared by structure" and a suppression comment.
- P-09: `ClaimPipeline._predicted_answer_path` is deleted rather than moved — it has no caller in `src` or `tests` (the identically named method on `PreprocessingPipeline` is a different function), and CLAUDE.md says delete unused code outright.
- P-10: Task 2 lands as three commits rather than one. Each moves a coherent group, rewires the pipeline for it, and leaves the full suite green, so a regression bisects to one seam instead of to a 1400-line reshuffle. The CONTEXT explicitly leaves commit count to discretion and prefers incremental move-then-wire.

Purpose: make the policy engine readable, unit-testable and cheap to change, so the next rule change edits one small module with a direct test instead of a 1414-line file with a graph fixture.
Output: a `compliance/policy/` package holding the routing, gating, checking, document, decision and payload policy as pure functions; one claim-artifact reader; a `claim_pipeline.py` that is graph wiring only; focused unit tests that target the extracted modules without graph or chat mocks; updated README / LOGIC references; SR-013 closed in the backlog.
