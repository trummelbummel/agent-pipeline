<objective>
SR-007 closes the last API-side integrity hole: today `GET /claims/{claim_id}` is a mutation. The handler calls `process_then_analyze`, which preprocesses the raw folder (OCR, Docling, the extraction LLM) and then runs the full `ClaimPipeline` analysis (six more LLM calls) and publishes a new generation under `results_dir`. A browser refresh, a monitoring probe, a retried request, or two operators looking at the same claim therefore each burn a full OCR + LLM pass and each publish a competing generation. That is the backlog risk "Duplicate OCR/LLM + interleaved writes", and it is also why `GET /claims` currently dies with a 500 on a single corrupt JSON file: `_load_optional_json` parses unguarded, so one bad artifact denies the operator every other claim in the list.

This plan separates the verb from the read. `GET /claims/{claim_id}` becomes a pure read of the generation SR-005 already publishes atomically — and structurally so, because the handler loses its `PreprocessingPipeline` and `ClaimPipeline` dependencies entirely. Analysis moves to a new sync `POST /claims/{claim_id}/analysis` (D-01) that returns the same `ClaimDecision` body the old GET returned, so the breaking change (D-03) is one method and one path segment for clients. Both endpoints read through one structured artifact reader that enforces the SR-005 generation contract on the way out, and the list endpoint reports an unreadable artifact as a per-item reason code on a 200 rather than a 500.

Concurrency is handled by a per-claim advisory lock under `results_dir/.locks/`, acquired non-blocking around the whole preprocess-plus-analyse span. Because the key is `claim_id` alone (D-02), two simultaneous requests for one claim collapse to exactly one analysis: the winner runs and returns 200, the loser is refused 409 before it touches OCR. That is what idempotency means for a sync endpoint with no client-supplied key — at most one analysis in flight per claim, never a duplicate pass, never two publications racing.

Locked decisions (from CONTEXT.md and `.gsd/steering-decisions-2026-09-29.md`):
- D-01: Sync `POST /claims/{claim_id}/analysis` — not a background job with a poll endpoint.
- D-02: Idempotency key = `claim_id` only.
- D-03: Breaking the existing GET-mutates clients is acceptable; GET becomes read-only immediately, with no transitional query flag.

Planner discretion (flagged; report in SUMMARY):
- P-01: The lock is an advisory `fcntl.flock` on `results_root/.locks/{claim_id}.lock`, acquired **non-blocking**. Non-blocking is the point: a blocking acquire would make the loser wait and then run its own full OCR + LLM pass, which is precisely the duplicate work the backlog names. Refusing with 409 is the only outcome that satisfies "cannot interleave writes" *and* "no duplicate OCR/LLM". A lock file is chosen over an in-process lock map because it also serialises the API against the CLI, and `flock` is preferred over a new dependency because `artifact_publication.py` already assumes POSIX (it fsyncs directory file descriptors) and a lock package would need a legitimacy audit for no added capability.
- P-02: The lock lives in `artifact_publication.py` beside `.staging` and `.runs` because it is a results-tree filesystem primitive that pairs with atomic publication, while the *policy* ("one analysis per claim, refuse contention") lives in `orchestration.py` next to the orchestration it guards. Lock files are never unlinked on release: unlinking races, because a waiter already holding a descriptor on the removed inode would not conflict with a fresh open of a recreated file. `.locks` is invisible to every claim discovery helper, all of which filter on a `claim` name prefix.
- P-03: The lock is taken at each entry point that analyses **one caller-supplied claim** — the API POST and CLI `--claim-id`. It is deliberately not pushed into `ClaimPipeline.analyze_claim`, because the API must hold it across preprocessing too (otherwise two POSTs both OCR and only then serialise), and a nested acquisition inside a locked span would self-conflict under `LOCK_NB`. The CLI batch loop is a follow-up, not a silent omission: contention inside a soft-fail batch needs a wait-versus-skip policy and a run-outcome status that no steering decision settles, and SR-005 already gives that path whole-generation atomicity per claim.
- P-04: A repeat POST after a completed analysis re-runs the analysis. POST is the explicit "analyse now" verb; `claim_id`-only idempotency (D-02) de-duplicates *concurrent* requests, it does not cache a result forever — with no content hash there is no way to know the inputs are unchanged, so refusing or replaying would be guessing.
- P-05: POST returns 200 with the `ClaimDecision` body, not 201 + Location. The analysis is a replaced singleton rather than a newly created collection member, and the body already is the representation a client would follow a Location to fetch.
- P-06: A corrupt list item is reported, not skipped and not fatal. `ClaimListItem.errors` maps artifact filename to a reason code, the artifact serialises as null, and the claim stays in the list. Skipping silently is the SR-006 defect in another costume (a claim that vanishes from a report), and a 422 for the whole list lets one corrupt file deny access to all 25 claims.
- P-07: The error reason codes are SR-005's own (`artifact_missing`, `run_id_missing`, `run_id_mismatch`) plus `invalid_json`, reused verbatim rather than translated into an API-local vocabulary, so a reason a client sees is the same string the evaluator and the publication module use. The new 404/409 details are stable snake_case codes (`analysis_not_found`, `analysis_in_progress`, `claim_not_found`); the existing 422 path-safety details keep their prose, which is out of this task's boundary.
- P-08: `GET /claims/{claim_id}` does **not** take even a shared lock. It validates the generation instead: during the SR-005 publish window, artifacts are promoted before the manifest commits, so a concurrent read can transiently observe `run_id_mismatch` and correctly gets 409. Taking a shared lock would make the read path create a lock file, and a read that creates files is exactly what this task removes.

Behaviour changes to record in the SUMMARY (intended, not regressions to fix here):
- `GET /claims/{claim_id}` no longer triggers analysis and returns 404 for a claim that has raw inputs but no published analysis. The old 404 meaning (missing raw folder) moves to POST.
- Clients that relied on GET to produce a decision must issue `POST /claims/{claim_id}/analysis` first (D-03).
- `GET /claims` items gain an `errors` field and stop returning 500 on corrupt artifacts.
- CLI `--claim-id` exits 1 when another analysis for that claim is already running.

Purpose: make reading a claim free and analysing it exclusive, so no operator can accidentally spend an OCR pass or publish a competing generation by looking at a claim.
Output: a read-only decision GET, a locked sync analysis POST, stable list error semantics, a per-claim lock primitive shared by API and CLI, tests covering read-only GET / POST analysis / contention / concurrency / corrupt artifacts, updated README, and SR-007 closed in the backlog.

The contract every task implements (D-01..D-03, P-01..P-08). Reason codes come from SR-005 verbatim (P-07).

**`GET /claims/{claim_id}` — read the published generation, never write.**

| Situation | Status | Detail / body |
|-----------|--------|---------------|
| unsafe claim id | 422 | existing path-safety prose |
| no analysis artifact under `results_dir/{claim_id}/` | 404 | `analysis_not_found` |
| artifact unparseable, or not a JSON object | 409 | `invalid_json` |
| artifact disagrees with the committed manifest | 409 | `run_id_missing` / `run_id_mismatch` / `artifact_missing` |
| valid generation | 200 | `ClaimDecision` (`predicted_answer` null when absent) |

The raw folder under `data_dir` is irrelevant to this endpoint — it reads `results_dir` only.

**`POST /claims/{claim_id}/analysis` — the only mutating claim verb.**

| Situation | Status | Detail / body |
|-----------|--------|---------------|
| unsafe claim id | 422 | existing path-safety prose |
| no raw claim folder under `data_dir/{claim_id}/` | 404 | `claim_not_found` |
| another analysis holds the per-claim lock | 409 | `analysis_in_progress` |
| analysis completes | 200 | `ClaimDecision` from the generation just published |
| pipeline raises | 500 | existing log-and-reraise behaviour |

**`GET /claims` — always 200, every claim folder listed.** Each item reads both optional artifacts through the same reader. A clean absent artifact is `null` with no error; an unreadable one is `null` plus `errors[{artifact filename}] = {reason code}`. `errors` is `null` when the item read cleanly.

**Lock.** `results_root/.locks/{claim_id}.lock`, exclusive and non-blocking, opened fresh per acquisition, released in a `finally`, never unlinked. Held across preprocess **and** analyse. Contention raises `ClaimAnalysisBusyError`, which the API maps to 409 and the CLI to exit 1.
