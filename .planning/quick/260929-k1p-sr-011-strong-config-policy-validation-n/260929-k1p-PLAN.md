<objective>
SR-011 turns `config.yaml` from a permissive document into a validated policy contract. Coverage routing becomes an explicit label-code -> branch map instead of meaning derived from list position, unknown keys fail hard, label vocabularies must be internally consistent, and every required-document / taxonomy cross-reference is checked when the config loads rather than discovered as a mis-routed claim.

Locked decisions (from CONTEXT.md and `.gsd/steering-decisions-2026-09-29.md`):
- D-01: Breaking named coverage keys NOW — no dual-read positional-to-named migration. The label-to-branch relation is an explicit map (`coverage.branches["1"] = cancellation`), not derived from the order of `labels`.
- D-02: Fail hard on unknown keys (`extra="forbid"`), not warn.

Planner discretion (flagged; report in SUMMARY):
- P-01 YAML shape: a single `analysis.coverage.branches` mapping of coverage code -> branch name, sibling to `labels`. Chosen over per-label objects because it keeps `labels` / `label_names` / `prompt` untouched, so only the coverage stage gains a field and every other stage config is unchanged.
- P-02 Model placement: a new `CoverageClassificationConfig(ClassificationConfig)` with a required `branches` field, used only by `AnalysisConfig.coverage`. The other four stages keep plain `ClassificationConfig`, because only coverage routes. Consequence: fixtures that share one `ClassificationConfig` instance across all five stages must build the coverage stage separately.
- P-03 `extra="forbid"` is applied tree-wide through one strict base model that every config model inherits, per the CONTEXT preference for AppConfig-tree consistency.
- P-04 `other_label` is NOT required to be a member of `labels`. Existing fixtures deliberately omit `False` from `labels` while setting `other_label: "False"`, and `abstention_labels()` already treats both as abstention. Requiring membership would be churn without a safety gain; the SUMMARY records this as the explicit rule.
- P-05 Branch values must be unique (two codes cannot share one branch), because the branch selects the document stage and the acceptable-document set; a many-to-one map would make `_document_stage_for_coverage` ambiguous about which taxonomy a claim was judged against.
- P-06 Alignment rule between `classification` and `analysis.coverage` is on the POSITIVE label sets (abstention labels excluded), which is what every existing config and fixture already satisfies. `label_names` are not cross-checked between the two sections.
- P-07 Error messages come from dedicated `ValueError` subclasses that build their message in `__init__` (the existing `ConfigFileNotFoundError` pattern), because ruff `TRY003` forbids long messages at the raise site. Pydantic wraps them into `ValidationError`, so callers still see one error type.
- P-08 Known limit, out of scope: SR-004's exact-probability tie-break still follows `labels` order (D-05 of SR-004), so reordering `labels` can still change which label wins a perfect tie. It can no longer change which branch a winning label routes to. The reorder test therefore uses unambiguous probabilities.

Purpose: remove the silent-policy-drift risk recorded in the backlog — a config reorder or a stale key currently changes claim routing (or is ignored) with no error.
Output: validated config models with named coverage keys, a keyed `_coverage_branch`, migrated config/fixtures, tests for unknown keys / duplicate labels / bad cross-refs / reorder-does-not-remap, and SR-011 closed in the backlog.
</objective>
